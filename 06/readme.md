# Основы интеграционных взаимодействий

## Теоретические задания

### 1. Схема взаимодействия микросервисов интернет-магазина
Участники:
- Сервис каталога – управляет товарами (описание, цена, наличие).
- Сервис корзины – хранит временные позиции пользователя.
- Сервис оплаты – обрабатывает платежи.
- Сервис доставки – рассчитывает стоимость и отслеживает отправку.

Взаимодействие (синхронное + асинхронное):
```
Пользователь
    │
    ▼
┌─────────────┐     (1) Запрос товаров         ┌──────────────┐
│   Клиент    │ ──────────────────────────────►│   Каталог    │
│ (браузер)   │ ◄───────────────────────────── │   (товары)   │
└─────────────┘      Список товаров            └──────────────┘
    │
    ▼
┌─────────────┐     (2) Добавить в корзину     ┌──────────────┐
│   Корзина   │ ◄───────────────────────────── │   Клиент     │
│             │ ──────────────────────────────►│              │
└─────────────┘ Содержимое корзины             └──────────────┘
    │                       
    │
    │ (оформление заказа)
    ▼
┌─────────────┐      (3) Запрос на оплату      ┌──────────────┐
│   Оплата    │ ◄───────────────────────────── │   Корзина    │
└─────────────┘      (итоговая сумма,          │              │
    │               данные карты-токен)        └──────────────┘
    │
    │ (синхронно: проверка баланса)
    │
    ▼
┌─────────────┐     (4) Успешный платёж        ┌──────────────┐
│   Оплата    │ ──────────────────────────────►│   Доставка   │
└─────────────┘     (заказ, адрес, сумма)      │              │
    │                                          └──────────────┘
    │
    │ (асинхронно: уведомления, логи)
    ▼
┌─────────────┐    (5) Событие "заказ создан"  ┌──────────────┐
│   Брокер    │ ──────────────────────────────►│   Email/СМС  │
└─────────────┘                                └──────────────┘
```

Передаваемые данные (основные поля):
- Каталог → клиент: id, name, price, stock, description, image_url.
- Клиент → корзина: user_id, product_id, quantity, selected_options.
- Корзина → оплата: order_id, user_id, total_amount, currency, payment_token (от платёжного шлюза), items[].
- Оплата → доставка: order_id, user_id, delivery_address, total_weight, preferred_date, payment_status.
- Оплата → брокер: событие payment_succeeded (или failed) с order_id.
- Доставка → брокер: событие delivery_status_updated с tracking_number.


### 2. Выбор типа взаимодействия (синхронный / асинхронный)

|                Сценарий                 | Рекомендуемый тип  | Обоснование |
|:---------------------------------------:|:------------------:|---|
|    Проверка баланса карты при оплате    |     Синхронный     | Пользователь ждёт ответа перед подтверждением заказа. Задержка неприемлема – требуется мгновенное решение (успех / ошибка). Операция короткая (обычно < 1 с).|
| Отправка email с подтверждением заказа  | Асинхронный | Не влияет на основной поток оформления. Допустима задержка в несколько секунд/минут. Можно ставить в очередь и обрабатывать в фоне. Повышает отказоустойчивость.|  
| Получение списка товаров в каталоге | Синхронный | Пользователь ожидает загрузку страницы. Ответ должен быть немедленным. Запрос простой (чтение БД или кэш), время выполнения минимально.|
| Генерация PDF-отчёта за месяц | Асинхронный | Операция может быть долгой (объём данных, рендеринг). Пользователю не нужно ждать – можно уведомить по готовности или дать ссылку на скачивание. Лучше выполнять в фоновом задании.|


### 3. Выбор брокера (Kafka / RabbitMQ)

| Сценарий | Предпочтительный брокер | Обоснование |
|:---:|:---:|---|
| Сбор логов со 100 серверов (миллионы записей/мин) | Kafka | Высокая пропускная способность, долговременное хранение (до нескольких дней), возможность повторного чтения, горизонтальное масштабирование. Логи – типичный use-case для Kafka (потоковая передача больших объёмов).|
| Обработка заказов в интернет-магазине (тысячи заказов/день) | RabbitMQ | Требуется гарантированная доставка, подтверждения (ack), маршрутизация по разным очередям (например, приоритеты, типы заказов). Объём невысокий, но важна надёжность и управляемость.|
| Real-time аналитика кликов на сайте | Kafka | Необходима низкая задержка и высокая скорость приёма событий. Kafka поддерживает разделение (partitions) для параллельной обработки и позволяет нескольким потребителям читать одни и те же данные. Идеально для стриминговой аналитики.|
| Отправка уведомлений пользователям | RabbitMQ | Относительно небольшие объёмы, требуется гибкая маршрутизация (например, по типу уведомления: email, push, SMS). RabbitMQ проще в настройке для сценариев "очередь задач" с подтверждением выполнения.|
